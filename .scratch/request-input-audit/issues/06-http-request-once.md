# 06：HTTP 调用失败、流式与重试的一次提交语义

本文验证通用 HTTP 观察链路与模型执行结果、流式完成和内部重试之间的独立性。

**What to build:** 管理员看到的是每次客户端提交的输入，而不是每次执行尝试或成功响应。上游失败、SSE、超时、断开和内部执行重试不导致漏掉已接收的合格输入或重复增记。

**Blocked by:** 01 — 最小安全 Chat Completions 审计闭环。

Status: ready-for-agent

**Spec:** [请求输入审计 spec](../spec.md)。主要覆盖 User Stories 22–28、52–55。

## Acceptance criteria

- [ ] 正常非流式与 SSE 流式 HTTP 请求在接收阶段采集，不能等待响应成功、首 token 或完整响应才决定记录。
- [ ] 相同客户端文本重新提交两次产生两条独立记录；客户端自报请求 ID 或会话信息不作为去重依据。
- [ ] 同一入站提交的上游重试、账号切换和流式首 token 前重试最多产生一条记录；宿主生成提交标识与内部执行标识不混淆。
- [ ] 插件或宿主发起的嵌套模型执行不当作新客户端提交，不因产生内部执行 ID 增加原提交记录。
- [ ] 上游失败、超时或客户端在合格输入已接收后断开，不取消本应排队保存的副本；异步保存失败另报缺口，不把模型失败当作采集失败。
- [ ] 可提取输入的模型/provider 路由前失败仍被观察；鉴权失败不记录。无法解析或不完整接收不捏造输入，应展示可确定的采集问题。
- [ ] 可控上游和公开响应验证观察不会改变请求或宿主已有成功、错误、流式及取消行为；审计不能额外返回拒绝状态。
- [ ] 管理详情不保存响应正文或状态跟踪信息来重建执行日志，仅使用 spec 允许的元数据和采集状态。
- [ ] 本票以已经可用的 Chat Completions 链路验收通用机制，并提供可复用外部行为场景；最终交付票将其回归到三协议，不能据本票宣称尚未实现的协议已验证。

## Testing decisions

在原系统行为边界通过可控上游产生失败、延迟、重试和流式行为；真实客户端断开并通过管理 API 等待可观察结果。不要靠固定 sleep、usage queue 或直接调用私有 lifecycle 方法证明入站一次语义。

## Implementation constraints

保持有界异步和常规 fail-open，不能为精准去重引入会话拼接、客户端可控唯一性或无限历史索引。缺口生命周期完整交互在后续 ticket 完善，但本票发生的异常已有基础可见诊断。
