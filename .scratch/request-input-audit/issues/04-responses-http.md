# 04：Responses HTTP 输入审计

本文定义 Responses HTTP 从本次客户端提交到管理员记录的协议扩展，不引入会话历史回查。

**What to build:** 管理员能够独立审查 Responses HTTP 的字符串和结构化新用户输入，看到正确协议、请求模型及提取状态；宿主执行所需的历史与协议改写不扩大审计范围。

**Blocked by:** 03 — Chat Completions 完整输入边界。

Status: ready-for-agent

**Spec:** [请求输入审计 spec](../spec.md)。主要覆盖 User Stories 11–24、26–28、31、40–41。

## Acceptance criteria

- [ ] 通过实际宿主观察扩展接收 Responses HTTP 本次原始协议输入，先于业务改写、路由和会话补全，不用转换后 Chat 消息替代。
- [ ] 字符串 input 作为本次用户文本处理；结构化输入仅取末尾明确的新用户消息，不回找旧 user、不跨消息拼接。
- [ ] 仅工具输出的续跑正常跳过；未知项或无法安全判断的格式产生提取不完整或解析缺口，不落盘完整 JSON。
- [ ] `previous_response_id` 不用于审计历史回查，不存该标识，不从宿主还原的上下文补正文；本次显式重发的文本作为独立新提交处理。
- [ ] 文本、非文本占位、普通文本不自动脱敏、空白、空输入和 UTF-8 截断沿用既定规则；工具结果内部内容不被提取。
- [ ] 管理列表和详情可识别 Responses 协议，显示客户端请求模型与记录状态；不能以实际上游模型代替请求模型，无法可靠确定时显示未知。
- [ ] 可提取的新输入即使模型/provider 路由前失败仍可查询；认证失败和未监控对象不产生输入记录。
- [ ] 可控上游和宿主公开响应证明观察、截断或解析失败不改变原始请求与调用结果；记录不依赖模型回复落盘。
- [ ] 专项持久化检查确认没有新增保存历史、指令、工具数据、非文本载荷、原始认证 Key 或整条 Responses 请求。

## Testing decisions

通过 Responses HTTP 提交和管理 API 查询验收字符串、结构化列表、工具续跑、previous_response_id、未知块与路由前失败；使用可控上游验证调用不变。共用原系统行为测试边界，不新增生产故障注入接口。

## Implementation constraints

本票不实现 WebSocket 握手或消息处理；其后续 ticket 复用已验证的 Responses 内容语义，但必须另外验证消息级原始输入来源。未完成 WebSocket 时明确显示实际支持范围。
