# 02：监控对象与采集配置生命周期

本文定义监控名单、名称、暂停及身份关联在变更和重启后的端到端行为。

**What to build:** 管理员通过页面添加、改名、移除监控对象以及暂停和恢复采集，不删除未过期历史；同一 Key 的对象关联保持稳定，不同 Key 轮换保持独立。

**Blocked by:** 01 — 最小安全 Chat Completions 审计闭环。

Status: ready-for-agent

**Spec:** [请求输入审计 spec](../spec.md)。主要覆盖 User Stories 1–10、32。

## Acceptance criteria

- [ ] 名单默认空；只能选择宿主内置客户端 Key 的无秘密标识，不粘贴、保存、回显原 Key 或 Key 字符片段，不能把上游账号列为客户端审计对象。
- [ ] 管理员可添加对象并设置名称；对象关联不依据名称或 Key 配置下标，监控操作不修改宿主 Key 列表和认证策略。
- [ ] 改名后旧记录与新记录统一显示当前名称，不保存每条记录名称快照；同名的不同 Key 不串联历史。
- [ ] 移除对象停止后续采集，但其未过期记录仍可查询；同一个原始 Key 重新加入沿用稳定对象及历史，不同 Key 轮换不自动合并。
- [ ] 配置列表重排、插入其他 Key、同值 Key 场景和进程重启不导致错误归属；无法可靠映射时不能猜测为另一对象。
- [ ] 全局主动暂停不采集新副本、不删除历史；恢复后正常续采。主动暂停和未监控是预期跳过，不报成丢失。
- [ ] 每次提交采用接收时配置快照，后续变更不追溯删除或改写已接收并入队的副本；接口为后续 WebSocket 下一提交生效提供一致语义。
- [ ] 对象配置和名称在重启后保留，未过期历史关联正确；非管理员无法读取或修改名单、名称或暂停状态。
- [ ] 页面能够区分受监控、已移除但有历史、主动暂停等状态，管理员仍能筛选旧对象，而不是因 Key 不再有效就无法查看历史。

## Testing decisions

通过管理界面或受保护 API 执行配置变更，再由真实 HTTP 提交和管理员查询观察结果；验证配置重排、重新加入和重启后的稳定关联。无需查询数据库私有表。新增字段和诊断接受禁止原 Key 持久化检查。

## Implementation constraints

沿用 spec 的内容最小化、管理鉴权、有界异步和 fail-open 约束，不增加用户身份、Key owner、名称快照、自动轮换合并或删除功能。本票只处理配置生命周期，保留期限与容量策略由其对应 ticket 完善。
