# 01：最小安全 Chat Completions 审计闭环

本文定义第一条可运行的客户端提交到管理员查看的审计链路，并验证宿主扩展的关键接入假设。

**What to build:** 在支持原生插件的官方 CLIProxyAPI v8.0.27 基线上增加最小只读 HTTP 观察契约，打通可信客户端身份、安全监控选择、插件采集、本地持久化和宿主管理页面。管理员选择一个无秘密审计对象标识并命名后，提交末尾纯文本，能够查看一条独立输入记录；模型请求行为不变。

**Blocked by:** None (can start immediately).

Status: ready-for-agent

**Spec:** [请求输入审计 spec](../spec.md)。主要覆盖 User Stories 1–3、11、22、25–26、33–34、38–39、52–53、59。

## Acceptance criteria

- [ ] 固定宿主版本和插件能力，提供可运行的最小宿主扩展与原生插件；不是用 mock 观察接口代替实际宿主接入验证。
- [ ] HTTP 观察位于客户端鉴权成功后、协议业务改写和模型路由前，获得本次提交的原始协议输入、宿主提交标识、接收时间和可信已认证身份；不是从上游 Auth、任意请求头或用量事件猜测客户端 Key。
- [ ] 宿主提供内置客户端 Key 的稳定无秘密标识供管理选择；不同 Key 分开，标识不依赖配置下标或名称，管理选择与认证结果能够正确关联。
- [ ] 名单默认空。管理员通过受保护 API 和最小页面选择对象并设置名称；未监控对象不采集，认证失败不生成对象输入记录，监控操作不修改宿主 Key 配置。
- [ ] 对含历史及指令的基本 Chat Completions 文本请求，仅保存末尾新用户纯文本和 spec 允许的元数据；基础工具续跑不回找旧 user。尚未支持的内容形式不得保存完整请求兜底或伪装完整。
- [ ] 使用有界异步队列和本地持久化，队列不保留整个请求；从第一条记录开始执行 64 KiB 安全上限和基础持久化空间保护，不依赖后续 ticket 才防止无界保存。后续 ticket 完善容量和保留行为。
- [ ] 管理菜单、无数据静态页面、受保护的列表及单条详情形成最小可浏览闭环；输入按纯文本显示。匿名及仅客户端 Key 不能读取记录、对象列表、配置或状态。
- [ ] 可提取末尾输入的模型/provider 路由前失败仍经过观察并产生输入记录；原始调用保持宿主应有错误，不被审计改为成功或另一种拒绝。
- [ ] 可控上游证实正常请求不被审计截断或修改；普通采集错误 fail-open，并有基础可见诊断。记录展示只对应已保存结果，不把入队冒充落盘。
- [ ] 插件存储、管理输出和诊断不新增保存原始认证 Key、完整请求、历史、系统指令、回复或其他禁止内容；应用层不加密，持久化权限受限。
- [ ] 明确展示当前阶段实际支持范围，不将未完成协议、WebSocket、过期清理或故障恢复宣称为已通过完整第一版验收。

## Testing decisions

遵循已确认的系统行为边界：真实 HTTP 提交到带扩展宿主与插件，通过受保护管理 API 查询，并由本地可控上游验证请求不变。补充最小浏览器管理入口验收和持久化隐私专项检查。不得为测试新增生产后门，不把数据库私有结构或宿主私有方法作为测试合同。

## Implementation constraints

- 语言、数据库和具体模块组织尚未选定；只为本闭环选择必要实现，并记录有实质取舍的决定，不能提前构建全部功能。
- 不使用全量请求日志或 usage queue 补取正文，不为调试保存完整请求。
- 原生插件同进程，常规 fail-open 不代表 native 崩溃隔离；不承诺零丢失、零延迟或吞吐。
- 只使用隔离环境、合成 Key 和可控上游；真实凭据、CI/CD、生产部署及 git commit/push 不在本票授权中。
